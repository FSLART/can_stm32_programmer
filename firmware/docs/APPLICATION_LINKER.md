# Create a new STM32 application project for this bootloader

**Configure the application's flash address, flash limit, stack and interrupt vectors once. Then build and upload its normal `.bin` for every update.** For the LART STM32F412RE bootloader, the application starts at **`0x08010200`**, has **`0x2FDD8` bytes** (196056) of usable flash and reserves the last **8 bytes of SRAM** for bootloader entry.

This guide explains the GNU `.ld` scripts generated by STM32CubeIDE. The method applies to other STM32 targets after adapting their bootloader layout. Use the exact chip's memory map; copying these addresses into another chip is not a port. Keil scatter files and IAR `.icf` files require the same reservations using their own syntax.

For a complete MCU port, use [PORTING.md](PORTING.md). For programming, use [UPLOADER.md](UPLOADER.md).

## Quick recipe for the STM32F412RE bootloader

In your **new application project**, rather than the bootloader project:

1. Copy its generated flash linker script to a project-owned file, for example `STM32F412RE_APP.ld`.
2. In its existing `MEMORY` block, change application `FLASH` to:

   ```ld
   FLASH (rx) : ORIGIN = 0x08010200, LENGTH = 0x2FDD8
   ```

3. Change `RAM` to:

   ```ld
   RAM (xrw) : ORIGIN = 0x20000000, LENGTH = 0x3FFF8
   ```

4. Keep the stack definition outside `MEMORY`:

   ```ld
   _estack = ORIGIN(RAM) + LENGTH(RAM);
   ```

   It now evaluates to **`0x2003FFF8`**, an eight-byte-aligned stack top. The bootloader request word remains at **`0x2003FFFC`**.

5. Keep `.isr_vector` first in `FLASH`, and keep the generated sections and startup symbols.
6. Select your new `.ld` file in **both Debug and Release** linker settings.
7. Configure application startup to use **`VTOR = 0x08010200`** (`USER_VECT_TAB_ADDRESS`, `VECT_TAB_OFFSET 0x00010200U`).
8. Clean/rebuild, check the map and vectors, then pass the application's `.bin` to `can_upload.py` or the GUI.

The remaining sections explain each step and how to calculate values for another STM32.

## 1 — Understand the flash addresses

The uploader adds a header before your raw application. The linker must account for that header when assigning execution addresses.

```text
Primary (application) slot, 0x08010000 - 0x0803FFFF
+----------------------+-------------------------------+------------+
| MCUboot header       | Your raw application          | Hash TLV   |
| added by uploader    | vectors, code, constants,     | added by   |
|                      | initial values for RAM data   | uploader   |
+----------------------+-------------------------------+------------+
^                      ^                                            ^
SLOT_START             APPLICATION_START = SLOT_START + HEADER      0x08040000 (staging slot)
```

| Name | Purpose | F412RE value |
| --- | --- | --- |
| Flash base | Bootloader reset/start address | `0x08000000` |
| Primary slot start | Packaged image header address | `0x08010000` |
| Application start | Raw application's vector table and linker origin | `0x08010200` |
| Staging slot start | Upload area; the bootloader copies from here into the primary slot | `0x08040000` |

**Use the application start as your application's `FLASH ORIGIN`.** Linking at the flash base would overlap the bootloader. Linking at the slot start would put the vector table where the bootloader expects the header.

Every upload is first written to the staging slot and then copied to the primary slot at the next reset, so there is **one application linker address**. Never link an application for `0x08040200`: code does not run from the staging slot.

## 2 — Calculate the addresses and sizes for your target

Get the slot layout from the **ported bootloader** ([boot_update.h](../Core/Inc/boot_update.h)) and the chip's reference manual. An application project does not decide these independently.

| Value | Meaning | Your target |
| --- | --- | --- |
| `F` | Flash base | |
| `O` | Primary slot offset from `F` | |
| `S` | Primary slot size | |
| `H` | Packaged image header size | |
| `E` | Space reserved at the end of the primary slot for metadata (0 here: the record lives in staging) | |
| `T` | Maximum complete trailing TLV block for the selected image format | |
| `A` | Application vector-table address | |
| `L` | Maximum raw application size | |
| `R`, `N` | Start and size of the RAM region used for the initial stack | |
| `Q` | Reserved RAM size for the bootloader request, including alignment/cache needs | |

For this bootloader's current unsigned header/payload/TLV format:

```text
A = F + O + H
Maximum packaged upload = S - E
L = S - E - H - T
Application FLASH: ORIGIN = A, LENGTH <= L
```

F412RE values:

```text
F = 0x08000000
O = 0x00010000
S = 0x00030000       192 KiB primary slot (sectors 4-5)
H = 0x00000200       512-byte header
E = 0x00000000       commit record is in the staging slot
T = 0x00000028       complete 40-byte SHA-256 TLV block

A = 0x08010200
L = 0x30000 - 0x200 - 0x28 = 0x2FDD8 = 196056 bytes
```

The raw application may extend up to **`0x0803FFD8` exclusive**. The 40-byte TLV then ends exactly at **`0x08040000`**, the start of the staging slot. Signed images need a larger TLV allowance; recalculate `T`, the linker limit and the uploader checks together.

**Do not use the chip's total flash size as the application length.** That would let code overlap the staging slot, which is erased by every upload.

## 3 — Select the correct linker script in CubeIDE

1. Create the application project for the exact MCU and generate its normal startup/HAL files.
2. Find its generated **flash** linker script, normally named `STM32<device>_FLASH.ld`.
3. Make a project-owned copy, such as `STM32F412RE_APP.ld`, and edit that copy. Keep the chip-generated script structure.
4. Open **Project Properties → C/C++ Build → Settings → MCU GCC Linker → General** and select the application script. Labels can vary with CubeIDE version.
5. Apply the setting to Debug and Release, or use the appropriate all-configurations selection.
6. Check the build console: the link command's **`-T`** option must name your application script.

If you also use CMake, update the application target's linker-script path there. CubeIDE and CMake settings are independent. Editing a file that the link command does not use has no effect; recheck after project regeneration or switching build configurations.

## 4 — Edit `MEMORY` and reserve the request flag

Complete example `MEMORY` block for the **F412RE application**:

```ld
MEMORY
{
  RAM   (xrw) : ORIGIN = 0x20000000, LENGTH = 0x3FFF8
  FLASH (rx)  : ORIGIN = 0x08010200, LENGTH = 0x2FDD8
}

_estack = ORIGIN(RAM) + LENGTH(RAM);
```

Replace the original block; do not paste a second `MEMORY` block containing the same region names. GNU linker `K` means 1024 bytes; hexadecimal lengths make byte-level reservations clear. [GNU MEMORY documentation](https://www.sourceware.org/binutils/docs/ld/MEMORY.html).

The last eight SRAM bytes, `0x2003FFF8` through `0x2003FFFF`, are outside `RAM`. The application stack grows downward from `0x2003FFF8`. The request word at `0x2003FFFC` is excluded from normal stack, heap, `.data` and `.bss` allocations. The bootloader linker uses the same `0x3FFF8` length.

For another STM32 with suitable reset-retained RAM:

```text
Reserved block = [R + N - Q, R + N)
Usable RAM length = N - Q
Initial stack = an eight-byte-aligned address below the reserved block
Request word = an agreed four-byte-aligned address inside the reserved block
```

Use the **same request address and magic in the application and bootloader**. Reserve it in both projects and any RTOS/external memory allocator. `volatile` does not reserve memory. Startup code that clears all SRAM can still destroy it even when it is excluded from `.bss`. The F412 has no data cache in front of SRAM, so `__DSB()` before `NVIC_SystemReset()` is enough. Full function and retention requirements: [RequestBootloader instructions](PORTING.md#step-9--add-requestbootloader-to-the-application).

**Avoid the four-byte stack-alignment trap:** reserving only the final word (`LENGTH = 0x3FFFC`) makes `_estack = 0x2003FFFC`, which is not eight-byte aligned; the bootloader's vector check and the uploader reject that stack pointer.

## 5 — Keep the generated sections and vector table

Keep `ENTRY(Reset_Handler)`. It names the ELF entry point; it does not set the vector-table address or the MCU's power-on boot selection.

At the start of your existing `SECTIONS` block, retain the generated vector-table section. You can add a symbol and assertions to make mistakes fail during linking:

```ld
SECTIONS
{
  .isr_vector :
  {
    . = ALIGN(4);
    __app_vector_start__ = .;
    KEEP(*(.isr_vector))
    . = ALIGN(4);
  } >FLASH

  /* Keep the rest of your generated sections here. */
}

ASSERT(ADDR(.isr_vector) == ORIGIN(FLASH),
       "Application vector table must start at FLASH origin")
ASSERT((_estack & 7) == 0,
       "Application stack must be eight-byte aligned")
```

Insert these changes into your existing script. This is a section example, **not a replacement for the entire generated linker file**.

Keep generated code/constants/unwind tables and C/C++ initialization arrays. Keep RAM initialization symbols such as `_sidata`, `_sdata`, `_edata`, `_sbss` and `_ebss` when your startup refers to them. In particular, retain the `.data` load mapping:

```ld
_sidata = LOADADDR(.data);

.data :
{
  . = ALIGN(4);
  _sdata = .;
  *(.data)
  *(.data*)
  *(.RamFunc)
  *(.RamFunc*)
  . = ALIGN(4);
  _edata = .;
} >RAM AT>FLASH
```

This places initialized data in RAM while storing its initial bytes inside the application's flash region. Review custom sections as well: fixed-address assets, persistent settings, DMA buffers and independently located load images can bypass the normal `FLASH` limit. The uploader accepts one contiguous application payload; widely separated load addresses create a huge, mostly empty `.bin`.

## 6 — Make application startup keep the correct interrupt vectors

**Changing the linker alone is insufficient.** The bootloader sets `VTOR = 0x08010200` before handoff, but a new project's `SystemInit()` may change it back to the flash base. The app can reach `main()` and then fail on its first interrupt if vectors point into the bootloader.

```text
FLASH_BASE + VECT_TAB_OFFSET = 0x08000000 + 0x00010200 = 0x08010200
```

### Option A — Cube-generated relocation settings

In the application's `system_stm32f4xx.c`:

```c
#define USER_VECT_TAB_ADDRESS
#define VECT_TAB_OFFSET 0x00010200U
```

Do not enable SRAM vectors. If supplied as compiler `-D` definitions, verify the generated source does not redefine them unconditionally. Update Debug and Release alike, and check the actual assignment to `SCB->VTOR`.

### Option B — Linker symbol in application `SystemInit()`

```c
extern uint32_t __app_vector_start__;

/* Inside application SystemInit(), after any generated vector-table assignment. */
SCB->VTOR = (uint32_t)&__app_vector_start__;
__DSB();
__ISB();
```

Preserve edits across Cube regeneration. The F412 vector table (113 entries) needs 512-byte alignment; `0x08010200` satisfies it.

## 7 — Build the raw `.bin` and let the uploader add the header

Enable binary output/post-build conversion in your application project. The equivalent GNU command is:

```powershell
arm-none-eabi-objcopy -O binary YourApplication.elf YourApplication.bin
```

For this workflow:

- Do not prepend a header in the linker script; the uploader adds it.
- Do not add a 512-byte blank prefix to the raw `.bin`.
- Do not use `--pad-to` to fill the slot; the uploader expects an unpadded image.
- Do not pass the bootloader `.bin` as the application.

The uploader cannot relocate a binary linked for the wrong address. Normal CAN programming example, from the `firmware` folder:

```powershell
.venv\Scripts\python.exe tools/can_upload.py "C:\path\to\YourApplication.bin" --channel COM5
```

ELF debugging through ST-LINK is a separate workflow. Loading a raw application ELF does not create the packaged header/hash expected by this bootloader. Either install a valid image through the uploader and then attach with the matching ELF symbols, or program the packaged `YourApplication.mcuboot.bin` at `0x08010000` with ST-LINK (the bootloader accepts a valid image placed directly in the primary slot). Do not erase the bootloader sectors.

## 8 — Verify before programming

### Check the build and map file

| Check | F412RE value |
| --- | --- |
| Link command uses the intended `.ld` | Your application script, both build configurations |
| `.isr_vector` starts at application origin | `0x08010200` |
| All application flash load bytes stay below the raw-image limit | End address no greater than `0x0803FFD8` |
| Initial stack is in valid RAM and eight-byte aligned | `0x2003FFF8` |
| Request word lies outside ordinary allocations | `0x2003FFFC` |
| Raw binary fits its limit | At most 196056 bytes |

```powershell
arm-none-eabi-objdump -h YourApplication.elf
arm-none-eabi-nm -n YourApplication.elf
```

Use `objdump`'s **LMA** column when checking the flash load image for sections whose **VMA** is in RAM. Initialized data consumes flash too.

### Check the first two binary words

The first word is the initial stack pointer; the second is the Thumb reset-handler address. Run this from the `firmware` folder to apply the uploader's packaging and vector checks without sending any CAN messages:

```powershell
.venv\Scripts\python.exe -c "import sys; from pathlib import Path; sys.path.insert(0, 'tools'); from can_upload import prepare_image; p = Path(sys.argv[1]); image = prepare_image(p.read_bytes()); print('Checks passed; packaged size:', len(image))" "C:\path\to\YourApplication.bin"
```

Expect an aligned stack in `0x20000000`–`0x20040000`, a reset-handler address with bit 0 set, and its remaining address bits inside the application payload starting at `0x08010200`. A passing vector check does not prove all code references/startup behavior are correct; inspect the map and test interrupts on hardware too.

## Troubleshooting

| Symptom | Likely cause / check |
| --- | --- |
| Uploader says application vectors are invalid | Wrong flash origin, wrong binary, unaligned stack |
| App reaches `main()` then faults | Startup restored VTOR to the bootloader address; check interrupt vectors |
| `.isr_vector` still appears at `0x08000000` | Build uses another linker script/configuration |
| RAM request does not enter bootloader | Flag overwritten by stack/startup/allocator |
| Raw `.bin` is unexpectedly huge | A section's load address is far from the application origin; inspect LMA |
| Linker reports flash overflow | App plus RAM initialization bytes exceeds 196056 bytes |
| Reset under debugger runs the loader | MCU reset starts the bootloader; it then starts the installed application |
| Debug works, Release fails | Different linker/startup definitions or missing `KEEP`/startup sections |

## Final checklist

- [ ] Application `FLASH ORIGIN` is `0x08010200` (primary slot + header).
- [ ] Application `FLASH LENGTH` is at most `0x2FDD8`.
- [ ] Debug and Release use the intended application linker file.
- [ ] Vector table is first in the raw image; generated startup sections/symbols remain intact.
- [ ] RAM length `0x3FFF8`, stack `0x2003FFF8`, request word `0x2003FFFC` reserved in both programs.
- [ ] Application startup keeps `VTOR = 0x08010200`.
- [ ] ELF/map/load addresses and raw binary pass inspection.
- [ ] Upload, reset, installation and interrupts checked on the target board.
